# Технический разбор выбора цели и атаки с движением

[← Скрипты и сценарии](structure.md)

[Читательская статья о выборе цели](../../docs/recon/world/combat/target_selection.md)

Статья объясняет, почему строй не всегда атакует ближайшего врага, как
рукопашники распределяются по нескольким целям и чем обычное движение
отличается от атаки с движением. Основные правила изложены языком игрока;
имена функций, режимов и полей собраны в
[технических подробностях](#технические-подробности-и-реализация) и
[источниках](#источники).

## Кратко

- Поиск идёт через **сетку** [^1]: карта разбита на ячейки фиксированного
  размера, каждая хранит свой список юнитов по игроку. Сканер обходит
  прямоугольник ячеек вокруг искателя, в каждой ячейке выбирает одного
  кандидата и в конце берёт ближайшего.
- Внутри ячейки порядок обхода **рандомизирован**: стартовый индекс задаётся
  со случайного места, и первый кандидат, прошедший все фильтры,
  становится выбором [^2].
- Для **юнитов ближнего боя** между ячейками работает балансировка нагрузки:
  расстояние до цели растёт на 12,5 % за каждого союзника, который уже
  выбрал её. Чем больше уже бьющих —
  тем целевая ячейка считается «дальше», и второй Пикинер предпочтёт
  другого врага. Это распределяет шеренгу по фронту, а не сваливает её
  на одного противника [^3].
- Для **стрелковых юнитов** балансировки нет — выбирается просто ближайший
  в радиусе.
- Стрелок в первые 0,25 игровой секунды после движения теряет до трёх
  клеток эффективного радиуса обнаружения. В покое полный радиус
  возвращается [^4].
- **Атака с движением** заставляет пехоту и кавалерию каждые 100 мс искать
  цель во всём радиусе. При обычном движении поиск ограничен передним
  конусом 30° [^5].
- **Артиллерия** стреляет в координаты, а не в привязанный к ним юнит.
  Точка не двигается за врагом [^6].

## Как игра выбирает цель

1. Игра берёт прямоугольник ячеек вокруг юнита.
2. В каждой ячейке она начинает перебор со случайной позиции и оставляет
   одного допустимого кандидата.
3. Стрелок сравнивает кандидатов по расстоянию. Рукопашник дополнительно
   считает, сколько союзников уже выбрали каждого врага.
4. Цели за пределами минимальной и максимальной дальности отбрасываются.
5. Для лечения, захвата и специальных задач компьютера действуют отдельные
   правила отбора.

Из-за этого соседние юниты одного строя могут выбрать разных противников,
даже если на экране один враг выглядит немного ближе другого.

## Что важно для управления

| Ситуация | Что произойдёт |
|---|---|
| Рукопашники входят в плотную шеренгу | Распределятся по фронту, потому что уже выбранная цель становится менее привлекательной. |
| Стрелки видят несколько целей | Каждый выбирает самостоятельно; общего автоматического фокуса нет. |
| Обычное движение мимо врага | Юнит реагирует в основном на противников в переднем конусе 30°. |
| Атака с движением | Поиск идёт во всех направлениях и регулярно обновляется. |
| Артиллерия стреляет по точке | Продолжает бить по координатам, даже если враг уже ушёл. |

## Технические подробности и реализация

<a id="1-точки-входа"></a>
### Точки входа

Четыре функции, через которые проходит весь процесс выбора цели:

| Функция | Когда зовётся | Что отвечает |
|---|---|---|
| `_unit_SearchVictim` [^7] | разовый поиск (отход стрелка, ручная переоценка) | прямой запрос «найди мне цель в кольце `[r0..r1]` от точки» |
| `_unit_SearchVictimOnProgress` [^8] | примерно каждые 100 мс | автоматическая атака и реагирование на врагов в процессе движения |
| `_unit_SearchEnemyScanCells` [^1] | вызывается обоими выше | обход ячеек сетки поиска и выбор наиболее подходящей цели |
| `_unit_SearchEnemyInCell` [^9] | вызывается из `_unit_SearchEnemyScanCells` | один проход по списку юнитов в одной ячейке |

Цикл такой: `_unit_SearchVictimOnProgress` определяет режим
(`scanmode`) и радиусы из `objprop`, затем вызывает
`_unit_SearchEnemyScanCells`. Тот для каждой ячейки получает кандидата
от `_unit_SearchEnemyInCell` и в конце выбирает того, у кого
минимальная относительная дистанция.

Сетка поиска (`gScanGrid`, `gScanGridUnits`) разбивает карту на
ячейки фиксированного размера отдельно для каждого игрока. В каждой
ячейке хранится список присутствующих юнитов и битовая маска
(`fplmask`, `myplmask`, `enemyplmask`). Это позволяет сразу отфильтровать
ячейки, в которых нет противника, и не открывать их вовсе [^10].

<a id="2-unitsearchenemyincell--выбор-внутри-одной-ячейки"></a>
### Выбор внутри одной ячейки

Возвращает один хэндл `goHnd` (или 0, если кандидата нет) [^9].

<a id="21-какие-игроки-рассматриваются"></a>
#### Какие игроки рассматриваются

Цикл по всем `gc_MaxPlayerCount` игрокам, фильтр по битовой маске
присутствия в ячейке и по принадлежности (свой / враг). В обычном режиме
обходятся только вражеские игроки. У лекарей (`scanmode = 1`) —
наоборот, только свои [^11].

<a id="22-случайный-стартовый-индекс-и-циклический-проход"></a>
#### Случайный стартовый индекс и циклический проход

Стартовый индекс задаётся как `floor(random × count)`, где `count` —
число юнитов игрока в ячейке. Далее идёт циклический проход по всем
`count` элементам, начиная с этого случайного индекса (по модулю
`count`). Первый кандидат, прошедший все проверки, объявляется
выбранным — соответствующая ветка делает `break(MAIN)` [^2].

Это значит: **внутри одной ячейки выбор статистически равномерен**
среди подходящих кандидатов. Если в ячейке четыре вражеских Мушкетера,
у каждого равные шансы стать целью.

<a id="23-фильтры-на-кандидата"></a>
#### Фильтры на кандидата

Минимальные:

- `trgHnd <> 0`,
- `trgHnd <> goHnd` (не сам себе),
- визуальное состояние не `gc_statetag_visual_hide`,
- основное состояние включает `gc_statetag_essential_none` (юнит не в смерти
  и не в рождении).

Радиус вычисляется по-разному для ближнего и дальнего боя. Сначала
определяется тип юнита по флагу `bmelee` (он истинен, если максимальный
радиус атаки не превышает `gc_unit_meleeattackradius`). Для стрелков из
радиуса вычитается случайный штраф `gc_obj_maxattackradiusdisp × uniqrnd`,
для рукопашников — нет [^12].

Константы: `gc_unit_meleeattackradius = 0.5` клетки,
`gc_obj_maxattackradiusdisp = 3` клетки [^13]. Стрелковый юнит
теряет до `3 × uniqrnd` клеток эффективного радиуса в момент сканирования.
Этот штраф применяется именно к выбору цели; штраф на дальность
выстрела при `standtime < 0.25` — отдельная история, описана в
[Как ведут себя стрелковые юниты §4](../../docs/recon/world/combat/ranged_units_behavior.md#4-штраф-к-дальности-при-движении-standtime).

Топологическая проверка: цель валидна, если она в той же зоне топологии,
что и атакующий, или (для дальнего боя) если дистанция в евклидовой норме
не превышает `maxRad + max((goY - trgY) × 2, 0)` (с бонусом за
возвышенность) [^14]. То есть рукопашник требует общей зоны (одна суша,
один остров), а стрелок может пробить либо общую зону, либо просто
прямую видимость в радиусе.

<a id="24-диспетчер-по-scanmode"></a>
#### Режимы отбора кандидата

Этот блок определяет, какой именно валидный кандидат выбирается.
Все ветки используют ранний выход `break(MAIN)` после нахождения первой
совместимой цели [^15]:

| `scanmode` | Где включается | Кого выбирает |
|---:|---|---|
| 0 (обычный) | обычный юнит | первый враг с `material ∈ {body, iron}` либо (если атакующий — здание) `material = wood`. Дополнительный фильтр `bcankill` через `kmask AND mmask`. |
| 1 (лечение) | у юнита `objprop.bpriest = True` | первый **свой** юнит с `hp < maxhp`. Если первый кандидат полностью здоров — функция выходит из цикла без результата. |
| 2 (поиск с запасным захватом) | по умолчанию для большинства юнитов без `bcapture` при периодическом обновлении | сначала ищет убиваемую цель (как режим 0); если не нашёл — отдельным проходом проверяет `bcapture && _unit_TestCapture(trgHnd)` и возвращает захватываемую. |
| 3 (только захват) | специализированный поиск, например для задач ИИ на захват | возвращает первую допустимую цель с `bcapture` и `_unit_TestCapture`, ничего другого не рассматривает. |
| 4 (диверсия ИИ) | специальные задачи ИИ | проходит **всех** кандидатов и выбирает цель с максимальным `weapon[0].damage`: самую опасную, а не ближайшую. |

«Первый» в режимах 0, 1, 2, 3 — это первый по тому самому случайному
обходу из §2.2. В режиме 4 цикл не обрывается ранним выходом —
`Result` обновляется по максимуму `damage`.

<a id="3-unitsearchenemyscancells--обход-ячеек"></a>
### Обход ячеек

Возвращает один хэндл `goHnd` или 0 [^1].

<a id="31-прямоугольник-ячеек"></a>
#### Прямоугольник ячеек

Через `_misc_CalcScanCellsMinMax` вычисляются индексы границ ячеек
вокруг позиции искателя; затем двойной цикл `i × j` по этому
прямоугольнику. `x1`, `y1` — индекс собственной ячейки искателя в
сетке поиска; `rx1` — радиус в ячейках, считается на верхнем уровне
как `floor(maxsearchdist / gc_scangrid_size) + 1`. То есть охватывается
квадрат `(2 × rx1 + 1)²` ячеек — обычно 3×3 или 5×5 [^16].

<a id="32-цикл-и-две-метрики"></a>
#### Цикл и две метрики

Для каждой ячейки `_unit_SearchEnemyInCell` возвращает одного кандидата.
Дальше его проверяют на принадлежность кольцу радиусов
(`minsearchdistSqr < distSqr < maxsearchdistSqr`) и обновляют сразу
**две метрики**: абсолютную минимальную дистанцию `minTrgHnd` и
относительную минимальную `minRelativeTrgHnd` (с учётом нагрузки на
цель). Возвращается именно `minRelativeTrgHnd` [^17].

Заметные моменты:

- **Кольцо радиусов.** Обе границы — `minsearchdist` (мёртвая зона
  у стрелков, в неё попадает противник вплотную) и `maxsearchdist`
  (внешний радиус прицельного выстрела). Стрелок в движении считает
  по `Sqr(maxsearchdist - 3 × uniqrnd)`. Стоящий стрелок и любой
  рукопашник — по `maxsearchdist²` [^4].
- **Две параллельные метрики.** `minTrgHnd` — просто абсолютно
  ближайшая цель. `minRelativeTrgHnd` — ближайшая с поправкой на
  «нагруженность» (см. §3.3).
- **Возвращается `minRelativeTrgHnd`** — то есть всегда вариант
  с балансировкой; абсолютная `minTrgHnd` рассчитывается, но в
  результате не используется. Авторский комментарий это прямо
  поясняет причину: из каждой ячейки выбирается только один юнит
  (`no help from relative dist cause we choose 1 unit from each cell`)
  [^18].

<a id="33-балансировка-нагрузки-для-рукопашников"></a>
#### Балансировка нагрузки для рукопашников

`stolist` — список юнитов, у которых поле цели текущего состояния
указывает на эту цель.
То есть это не «текущие в радиусе атаки», а **сколько в принципе идут
или собираются бить** конкретно этого противника. Для рукопашников
относительная дистанция считается как `distSqr × (1 + stolist.GetCount × 0.125)`,
то есть «загруженная» цель эффективно отодвигается [^3].

Эффект для рукопашника при выборе:

| `STO_count` | Множитель к `distSqr` | На квадрате расстояния |
|---:|---:|---|
| 0 | ×1.000 | реальная дистанция |
| 1 | ×1.125 | +6.1% линейной дистанции |
| 4 | ×1.500 | +22.5% |
| 8 | ×2.000 | +41.4% |
| 16 | ×3.000 | +73.2% |

Цель, к которой уже бегут восемь твоих, эффективно «отодвигается»
на 41% — и второй Пикинер, скорее всего, выберет другого врага в той же
ячейке. Это делает строй более размазанным по фронту.

Для стрелков балансировки нет. Все Мушкетеры одного отряда обычно
валят одну ближайшую цель; распределение получается естественно —
через рассеяние выстрелов и порядок обхода ячеек, а не через явную
метрику.

<a id="34-ранний-выход-для-рукопашников"></a>
#### Ранний выход для рукопашников

Если рукопашник нашёл цель **внутри половины ячейки поиска**
(около 4 клеток)
и улучшил `relativeDist`, цикл по ячейкам обрывается. Дальше искать
«более балансировочно подходящего» противника не имеет смысла —
текущий и так совсем рядом. Константа `cOkDist = (gc_scangrid_size / 2)²`
вычисляется внутри функции [^19].

Для стрелков такого выхода нет — они всегда обходят весь прямоугольник.

<a id="4-unitsearchvictimonprogress--периодический-поиск"></a>
### Периодический поиск

Автомат состояний юнита обновляет поиск примерно каждые 100 мс. На этом
шаге игра решает, кого атаковать прямо сейчас [^8].

<a id="41-радиусы"></a>
#### Радиусы

Базовые значения берутся из `objprop`: `searchdist = objprop.searchradius`,
`minsearchdist = objprop.minattackradius`. К стрелку (когда
`minsearchdist > gc_unit_meleeattackradius`) добавляется бонус с
возвышенности — `searchdist += goHeight × 2`, если `goHeight > 0`.
Для рукопашника при охране (`Guard`) `searchdist` ограничен сверху
константой `gc_gameplay_meleeguardmaxsearchdist` — охранник не уходит
далеко [^20].

Бонус с возвышенности подробнее — в
[Как ведут себя стрелковые юниты §7](../../docs/recon/world/combat/ranged_units_behavior.md#7-high-ground--бонус-с-возвышенности).

<a id="42-выбор-режима-поиска-scanmode"></a>
#### Выбор режима поиска

Священник идёт в `scanmode = 1`. Все юниты, которые сами захватываются
(`bcapture` — например, артиллерия), а также водные и здания — в
`scanmode = 0` (только убивать). Все остальные не-захватываемые
наземные юниты (пехота, кавалерия) — в `scanmode = 2`: приоритет убить,
при провале — захватить [^21].

То есть пехотный юнит **по умолчанию пытается захватить** беззащитную
пушку или склад, если ничего убиваемого рядом нет.

<a id="43-диспетчер-обхода"></a>
#### Выбор способа обхода

В зависимости от среды и числа ячеек выбирается одна из трёх процедур
обхода: для водных юнитов — `_unit_SearchEnemyScanCellsShips`, для
дальнобойных (`_misc_GetShotPointsCount > 0`, артиллерия и башни) или
большого радиуса — `_unit_SearchEnemyScanCellsLongRange`, для
обычных — `_unit_SearchEnemyScanCells` [^22].

Дальний поиск обходит до 18 ячеек (`cLongRangeTryNum = 18`) и выбирает
**первую попавшуюся** валидную цель — он не ищет минимум.

## 5. Атака с движением

В Cossacks 3 атака с движением выглядит для игрока как одно действие, но
в коде — это **несколько разных ордеров** в зависимости от типа юнита
и того, как игрок навёл прицел.

<a id="51-для-пехоты-и-кавалерии--gcobjordertypemove-с-подрежимами"></a>
### 5.1. Пехота и кавалерия

`progress` ордера хранит подрежим [^5]:

| Подрежим | Константа | Поведение |
|---|---|---|
| `move_mode_default` | 0 | обычное движение к точке |
| `move_mode_attack` | 1 | движение с атакой: каждое периодическое обновление вызывает `_unit_SearchVictimOnProgress` и при наличии цели отдаёт текущий приказ через `_unit_OrderAttack` |

Дополнительно есть глобальный флаг профиля
`gProfile.bsearchenemyinfront` (по умолчанию `True` [^23]). Он добавляет
**умный поиск** для `move_mode_default`: если найдена потенциальная
цель и угол между направлением движения и направлением на неё не
превышает `cMinAngle = 30°`, юнит автоматически разворачивается в
атаку [^24].

То есть при включённом умном поиске обычное движение (правый клик)
тоже ловит врагов, но **только тех, кто в 30°-конусе впереди**. Враги
по бокам и сзади игнорируются. При движении с атакой
(`move_mode_attack`) такого ограничения нет — берётся ближайший враг
куда угодно.

<a id="52-для-артиллерии--gcobjordertypeattackpoint"></a>
### 5.2. Артиллерия

`_player_OrderUnitsToAttackPoint` обрабатывает только юниты с
`objprop.bartprepare = True`. Для каждого такого юнита снимается
`bstandground`, выставляется `bsearchenemy`, опционально очищаются
прежние ордера и выдаётся `_unit_OrderAttackPoint` с координатами [^6].

`bartprepare = True` стоит у Пушки (`cannon`), Гаубицы (`howitzer`)
и Рибадекина (`framegun`; точные
ветки в скрипте — см. [^25]). Эти юниты:

1. Получают `gc_obj_order_type_attackpoint` с координатами точки.
2. При каждом периодическом обновлении в `_unit_TryAttackPoint` [^26] проверяют,
   находится ли точка в радиусе, и стреляют по ней. Точка ни от кого
   не зависит — это просто координата.
3. Урон по области получает каждый, кто оказался в радиусе взрыва (см.
   [Как рассчитывается урон §6.5](../../docs/recon/world/combat/combat_damage_pipeline.md)).
4. Из-за `bsearchenemy := True` артиллерия параллельно сама выбирает
   цели через `_unit_SearchVictimOnProgress`, если в её обычном радиусе
   появился противник, — но текущий `attackpoint`-ордер не сменит,
   пока не отстреляется.

Отличие от атаки с движением: артиллерия **стреляет по координате**, даже
если цель ушла. Это удобно для подавления и мортирной поддержки за
линию видимости. Но если враг отбежал, обычная артиллерия с приказом
стрельбы по точке продолжает бить по пустому месту до новой команды.

### 5.3 Через интерфейс

Интерфейс отправляет пакет, который обрабатывает `units/global.inc/readorder.inc`.
В нём есть три точки, которые ставят `bsearchenemy := True` [^27],
и все они соответствуют ордерам, после которых юнит должен сам искать
противника:

- обычное движение `move`,
- `move_mode_attack`,
- `attackpoint` (артиллерия).

То есть «нашёл врага — переключился» работает **всегда**, кроме
случаев, когда `bstandground` явно стоит и `standtime > 0`. Это поведение
описано в
[Как ведут себя стрелковые юниты §1-2](../../docs/recon/world/combat/ranged_units_behavior.md#1-standground-vs-обычный-режим).

## 6. Что отсюда следует для микроконтроля

- **Фокус-стрельба сама по себе не работает.** Стрелки одного отряда
  выбирают цели индивидуально: случайный старт внутри ячейки плюс
  `minRelativeTrgHnd` по ячейкам, — а не координируют общую цель.
  Чтобы все 36 Мушкетеров стреляли в одного врага, нужно явно дать
  `OrderAttack` (правый клик по цели), и даже это удерживается
  не жёстко: после убийства или ухода врага из радиуса каждый юнит
  переоценит самостоятельно.
- **Рукопашники распределяются** по фронту через балансировку
  служебного списка целей (`STO`):
  каждый следующий Пикинер в строю учитывает, сколько уже бьёт
  текущего кандидата, и при равных дистанциях скорее выберет
  другого. Поэтому строй Пикинеров естественно охватывает шеренгу
  врагов, а не сваливается в одну точку.
- **Стрельба с отходом** ограничена углом `cMinAngle = 30°`. Если
  стрелок двигается обычным приказом движения, без атаки с
  движением: он замечает
  врагов только в переднем конусе. Кавалерист, заходящий с тыла или
  фланга, не активирует автоатаку у Мушкетера, идущего вперёд по
  правому щелчку. Нужен либо `move_mode_attack`, либо явный приказ
  остановиться.
- **Артиллерия по точке полезна как запрет зоны.** Поставленная на
  Пушка при стрельбе по точке не пересчитывает цель — она будет
  стрелять по координате с заложенным разбросом (`dispertion`),
  накрывая уроном по области всех, кто туда
  заходит.
- **Стрелок в движении эффективно «ниже» на 3 клетки** по радиусу
  обнаружения: `maxRad -= 3 × uniqrnd` пока `standtime < 0.25`.
  Юнит с высоким `uniqrnd ≈ 0.9` теряет сразу 2.7 клетки, низкий
  `≈ 0.1` — 0.3 клетки. То есть в одной шеренге часть Мушкетеров
  «увидит» цель раньше, остальные — позже.
- **Диверсант под управлением ИИ целит в максимальный урон.** В
  режиме `scanmode = 4` (специальные задачи ИИ) юнит выбирает
  не ближайшего, а самого опасного врага по `weapon[0].damage`. Это
  не «обычный» ИИ; см. [Как играет компьютер](../../docs/recon/systems/ai_behavior.md), раздел
  «Открытые вопросы».

<a id="7-лечение-духовными-лицами-bpriest"></a>
## 7. Как духовные лица выбирают раненых

Капеллан, Поп, Мулла и Падре — особый класс юнитов. Они сканируют
**только союзников** и выбирают первого встреченного раненого;
если первый кандидат уже полностью здоров — выход без результата.

Лечение обрабатывается отдельной веткой расчёта (см.
[Как рассчитывается урон §5](../../docs/recon/world/combat/combat_damage_pipeline.md)) [^32]. Формула:

```
target.hp += weapon.damage              # БЕЗ shield, БЕЗ protection
target.hp := min(target.hp, target.maxhp)
```

Пауза лечения равна нулю (`heal pause = 0`): лекарь восстанавливает
здоровье каждый цикл анимации (около 0,7 игровой секунды), пока
цель не будет полностью здорова.

| Юнит | Лечение за удар | Дальность (пиксели / клетки) | Где доступен |
|---|---:|---|---|
| Капеллан (`priest`) | 20 | 0–400 / 7,5 | большинство европейских наций |
| Поп (`pope`) | 25 | 0–350 / 6,6 | Папская область / Венеция |
| Мулла (`mullah`) | 15 | 0–500 / **9,4** | Турция / Алжир (самая большая дальность) |
| Падре (`padre`) | 30 | 0–400 / 7,5 | Испания / Португалия (самое сильное лечение) |

### 7.1. Стратегические свойства

- **Лечение игнорирует броню и щит** — восстанавливает здоровье на
  полное `weapon.damage` независимо от защиты цели.
- **Несколько лекарей лечат одну цель параллельно**: Рейтар с
  282 здоровья получает от четырёх Капелланов +80 здоровья за
  цикл, или около 115 в секунду.
- **Мулла имеет самую большую дальность** — лечит из второй
  линии, недосягаем для ближнего боя.
- **Падре самый эффективный** (30 за удар) — испано-португальская
  армия очень живуча.
- Лекари сами уязвимы (мало здоровья, нет брони) — приоритетная
  цель для рейдов.

### 7.2. Конверсии нет

В отличие от миссионеров в Age of Empires II, в Cossacks 3 лекарь —
**только лекарь**. Никакой конверсии вражеских юнитов в свои в
скриптах нет. См. также [Как захватываются здания и юниты](../../docs/recon/world/economy/capture_mechanics.md)
§7.

## 8. Реакция отряда на полученный удар

Любой не-артиллерийский юнит, получивший урон в `_misc_DoDamage`,
переключает свой `TSquad.fAgressive := True` и обновляет
`fLastBattleTime` [^33]. Эффект: **один поражающий выстрел / удар
по любому юниту отряда переводит весь отряд в боевой режим** —
все юниты начинают активно искать врага и контратаковать.

### 8.1. Стратегические следствия

- **Поклёвывание ИИ одним лучником** активирует **весь** отряд
  ИИ. Можно использовать как отвлечение: один разведчик дразнит
  армию, остальные обходят с фланга.
- **Артиллерия ИИ — исключение** (особый случай в коде): не
  переключается в `fAgressive` от удара, продолжает работать в
  своём приказе.
- **Скрытая собирательская деятельность** (рейд крестьянами в
  тыл) — **не атаковать** вообще, иначе вся армия зашевелится.

См. также [Как рассчитывается урон §8](../../docs/recon/world/combat/combat_damage_pipeline.md)
о том же эффекте со стороны формулы урона.

## 9. Рассеяние и точность выстрела

Каждый выстрел снаряда рассеивается относительно цели по
формуле в `_weapon_CalcShotDispertion` [^34]:

```
maxdisp = dist × disp × 0.0267         # в клетках
shot_x  = target_x + (1 − random × 2) × maxdisp
shot_z  = target_z + (1 − random × 2) × maxdisp
```

`dist` — дистанция до цели (клетки), `disp` — `weapon.dispertion`
(клетки, после `_misc_PixelsToTiles`). **Чем дальше — тем больше
рассеяние**, линейно.

<a id="91-базовые-значения-разброса-dispertion"></a>
### 9.1. Базовые значения разброса

| Оружие | Разброс (пиксели / клетки) | Отклонение на 15 клетках |
|---|---:|---:|
| Стрелец, мушкетный выстрел (`SHOTMUSKET`) | 200 / 3,75 | ±1,50 клетки |
| Лучник, стрела (`STRELA`) | 175 / 3,28 | ±1,31 клетки |
| Лучник, огненная стрела (`OSTRELA`) | 200 / 3,75 | ±1,50 клетки |
| Мушкетер, базовое значение | 250 / 4,69 | ±1,88 клетки |
| Пушка, ядро (`PPOINTT`) | ~250 / 4,69 | ±1,88 клетки |
| Башня, ядро (`PPOINTTTOW`) | ~100 / 1,88 | ±0,75 клетки |
| Яхта / Галера, ядро (`PPOINTTKOR`) | 25 / 0,47 | ±0,19 клетки |

### 9.2. Шанс попасть в юнит размером 1×1 клетка на дистанции `d`

- Если `2 × maxdisp ≤ 1` → ~100 % попадание.
- Если `2 × maxdisp > 1` → шанс ≈ `1 / (2 × maxdisp)` попасть в
  нужный квадрат.

Пример: Мушкетер (`disp = 3.75`) на 15 клетках →
`maxdisp = 1.50`, окно ±1.50 = 3.00 → шанс попасть в цель 1×1 ≈
**1/3 = 33 %** одним выстрелом. Поэтому расчёт **времени до убийства
для дальних пуль и
стрел в идеализированных матрицах занижен в 3 раза**.

<a id="93-улучшения-разброса-dispertion"></a>
### 9.3. Улучшения точности

Только для **артиллерии**:
- `aca.20` («Исследовать новые прицельные приспособления для
  артиллерии»): **−35 % разброса**.
- `aca.27` («Развивать математику»): **−35 %** (накапливается с
  `aca.20`).

Для Мушкетеров и Лучников **прямого** улучшения разброса **нет**.

       var angle : Float = VectorAngle(dirx, 0, dirz, dirx2, 0, dirz2);
       if (angle < cMinAngle) then

    end;

## Математика применения: порядок и комбинирование

**Главное наблюдение:** в Cossacks 3 порядок исследования апгрейдов **не влияет** на финальные параметры юнита/здания почти во всех случаях, даже когда к одному параметру применяются flat-бонус и процентный бонус из разных мест (например, кузница `+5 урона` и академия `+25% урона`). Это отличается от наивной арифметики, где `(B+5)·1.25 ≠ B·1.25 + 5`.

Причина в реализации `_player_ApplyUpgrade` (`scripts/lib/player.script:1707..1983`): каждый апгрейд аккумулирует своё слагаемое в **отдельное поле** объекта (`damagestatic`, `damagepercent`, `protection[kind]`, `shield`, `resefficiency[*]` …), а итоговое значение **пересчитывается из неизменной базы** (`damageinit`) по формуле, использующей только суммарное состояние, а не предыдущее значение. Никакой running-цепочки нет.

### Урон (`+damage` flat и `+damage %`)

Хранятся **три** поля: `damageinit` (база), `damagestatic` (сумма всех flat-бонусов), `damagepercent` (сумма всех %-бонусов). На каждом апгрейде:

```pascal
// gc_upg_type_damage  (player.script:1764)
damagestatic  := damagestatic  + round(value);
damage := floor((damageinit + damagestatic) * (1 + damagepercent/100));

// gc_upg_type_damageperc  (player.script:1783)
damagepercent := damagepercent + round(value);
damage := floor((damageinit + damagestatic) * (1 + damagepercent/100));
```

→ Финальный `damage = floor((damageinit + Σflat) · (1 + Σ%/100))` независимо от порядка.
Пример: база 10, бонусы `+5` и `+25%`. В обоих порядках получится `floor((10+5)·1.25) = 18`. В обычной арифметике (10+5)·1.25 = 18.75 vs (10·1.25)+5 = 17.5 — то есть разница, которой в Cossacks нет.

### Защита (`protection`, `shield`, оба только flat)

`protection[kind] += value`; `shield += value`. Чистая сумма — порядок безразличен.

### HP юнита (`lifeperc`, %)

`maxhp = round(maxhp · (1 + value/100))`. Накопительное умножение — коммутативно (`H·(1+a)·(1+b) = H·(1+b)·(1+a)`). Порядок не важен (с точностью до округления, см. ниже).

### Эффективность добычи (`effectfood/wood/stone` + их `…perc`)

Один и тот же массив `resefficiency[res]` (база = 100). Все четыре варианта (`flat`/`perc`) делают **одно и то же**:

```pascal
resefficiency[res] := resefficiency[res] + round(value);   // перцент-варианты тоже += value, не *=
```

→ Сумма всех val, порядок безразличен. **Нюанс:** flat и % здесь неразличимы — оба прибавляются. Множитель `resefficiency/100` затем применяется в формуле добычи (`_unit_GetPeasantResPortion`).

### Жизнь поля (`fieldlifeperc`, %)

`fieldlife += value`. Аддитивно (не мультипликативно). Порядок безразличен.

### Время постройки (`buildtimeperc`, %)

`buildtime *= (1 + value/(100·100000))` — накопительное умножение, коммутативно. Странный делитель `100·100000` объясняет хранение val как `-7500000` для −75% (см. примечание про scale в начале документа).

### Скорострельность / дальность / разлёт (`attpauseperc`, `attrangeperc`, `attdispertionperc`)

Все вида `field *= (1 + value/100)` — накопительное умножение, коммутативно.

### Цена (`priceperc`, %)

`price[j] = round(price[j] · (1 + value/100))`. Умножение коммутативно, но `round()` после каждого шага **может** дать разницу ±1 при разном порядке. На практике несколько `priceperc` на один объект почти не пересекаются.

### Рыболовство (`fishingperc`, %)

`fishingmax = round(fishingmax · (1+value/100))`, та же ситуация — теоретически ±1 от порядка из-за округления, на практике на лодку приходится один апгрейд.

### Скорость движения (`speedperc`, %) — **аномалия**

```pascal
// player.script:1930
speed := 1/(speed*(1+value/100));
```

Поле `speed` хранится как `1/v` (обратная величина), и операция инвертирует значение. Два последовательных применения дают `V_0·(1+p₂)/(1+p₁)` — **порядок-зависимо** и явно баг. Безопасно в продакшене только потому, что в данных существует **ровно один** `speedperc`-апгрейд на тип юнита (`aca.28` — скорость кораблей +40%), повторно применить его нельзя (`upgstate.done := True` блокирует).

### Сводная таблица

| itype | Накопление | От порядка зависит? |
|---|---|---|
| `damage` (flat) | `damagestatic += val`, пересчёт от `damageinit` | Нет |
| `damageperc` (%) | `damagepercent += val`, пересчёт от `damageinit` | Нет |
| `protection`, `shield` | `+= val` | Нет |
| `lifeperc` (%) | `maxhp = round(maxhp·(1+val/100))` | Нет (коммут. ум-е; round может дать ±1) |
| `effectfood/wood/stone[perc]` | `resefficiency += val` | Нет (flat и % неразличимы) |
| `fieldlifeperc` | `fieldlife += val` | Нет |
| `buildtimeperc` (%) | `*= (1+val/(100·10⁵))` | Нет |
| `priceperc` (%) | `= round(·(1+val/100))` | Только по округлению (±1) |
| `attpauseperc/rangeperc/dispertionperc` | `*= (1+val/100)` | Нет |
| `fishingperc` (%) | `= round(·(1+val/100))` | Только по округлению (±1) |
| `speedperc` (%) | `speed = 1/(speed·(1+val/100))` | **Да, но в данных только 1 апгрейд** |

### Практический вывод

**Апгрейды можно покупать в любом удобном порядке — финальные ТТХ юнита/здания идентичны.** Порядок имеет значение только для **экономики во времени** (что построится раньше) и для последовательности **enable**-апгрейдов (фрегаты, линейные корабли, многоствольное орудие) — но не для арифметики бонусов. Это упрощает планирование: в симуляторах экономики/боя можно агрегировать апгрейды как множества, не отслеживая последовательность их применения.

Единственные тонкие места — `priceperc`, `lifeperc`, `fishingperc` (накопительный `round()` может дать ±1 от порядка) и баг `speedperc` (но повторно не применяется). Для всего остального математика устроена так, что результат — функция от множества исследованных апгрейдов, а не от истории.

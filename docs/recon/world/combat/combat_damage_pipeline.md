# Как рассчитывается урон

[← Как устроена игра](../../README.md)

Статья отвечает на практический вопрос: почему один и тот же выстрел по
разным целям снимает разное количество здоровья. Ниже разобраны шесть
последовательных поправок к урону, мирное время, сценарная неуязвимость,
дружественный огонь и связь с построениями, захватом и лечением.

> **Базовые таблицы** (типы оружия, шкала `protection[kind]`, числа по
> каждому юниту) — в [Бой и движение](../../../reference/02_combat/README.md).
> Этот документ объясняет **процесс**, а не цифры.

## Кратко

- Расчёт начинается, когда снаряд достигает цели или рукопашный юнит
  завершает удар.
- Шесть последовательных модификаторов: снижение урона по быстрой
  коннице → щит → бонус строя → защита по типу → лечение
  капелланом → минимальный урон.
- Попадание в голову — редкий отдельный бонус для пуль и стрел;
  по зданиям он не срабатывает.
- Минимум один пункт здоровья снимается всегда, даже если все
  модификаторы вытеснили урон в отрицательное значение.
- Мирное время и сценарная неуязвимость проверяются **до** формулы и
  могут полностью отменить урон.

Если нужен только практический результат, достаточно этого списка. Далее
каждый шаг разобран с формулами, внутренними полями и ссылками на код игры.

<a id="1-точка-входа-и-предусловия"></a>
## 1. Когда начинается расчёт

Расчёт начинается в момент попадания. Конкретный кадр удара задаётся
анимацией юнита; техническая цепочка описана в
[системе анимаций §5](../../../../internals/engine/animation_system.md).

До формулы игра убеждается, что цель существует, ещё жива и допускает
обычный урон [^1]. Затем отдельно проверяются сценарная неуязвимость и
мирное время [^2]. Только после этого в расчёт поступают базовый урон,
тип оружия и выбранная цель. Имена функции и её пяти аргументов приведены в
[технических подробностях](#технические-подробности).

---

## 2. Шаги формулы

После всех проверок включается основной конвейер. На каждом шаге
переменная `damage` (изначально `damage := indamage`) корректируется.

### Шаг 1. Снижение урона по быстрой коннице

Если цель — лёгкая конница в движении (`usage = gc_obj_usage_fasthorse`,
`statestag` содержит `gc_statetag_move_walk`) и снаряд — пуля или
стрела, скрипт **отнимает 5 единиц** перед всеми остальными
расчётами [^1]. Это эмулирует «пуля задела вскользь».

`bCanHeadShot` истинно только для Силы выстрела (`bullet`) или
Стрел (`arrow`) и только если
цель не здание (`not bbuilding`). Для копья / меча / ядра пушки
этот шаг пропускается.

### Шаг 2. Щит цели

Если здание достроено (`bbuilt = True`), вычитается полный
`shield` цели; если ещё строится (`bbuilt = False`) — только
треть `shield DIV 3` [^7]. `shield` берётся из `data.json` [^3].

Это даёт типичный приём: атаковать башню противника **пока она не
достроена** — урон проходит почти полностью, защиты практически нет.

### Шаг 3. Бонус строя цели

Если у цели есть привязанный отряд (`squad >= 0`), скрипт
вытаскивает `pSquad2` из `gPlayer[target.pl].squads` и применяет
бонус щита формации: при `fHoldMode = True` берётся
`fAddShieldHold`, иначе `fAddShield` — итог вычитается из урона
(обычно `+2` на ходу и `+7` при удержании позиции). См.
[Построения и их боевые бонусы §3](formations.md). Если цель не в строю
(`squad = -1`), шаг пропускается.

### Шаг 4. Защита по типу оружия

Из урона вычитается `target.protection[weapkind]` — массив из 7
значений по `gc_obj_weapon_kind_*` [^4]. Например, у пехотинца с
лёгкой защитой `protection[bullet] = 1`, `protection[arrow] = 2`,
`protection[pike] = 0`. У тяжёлой кавалерии `protection[bullet] = 1`,
но `protection[sword] = 4`, поэтому сабельный удар часто проходит
через 4 единицы кирасы.

### Шаг 5. Лечение капелланом (исключение)

Если **атакующий** — Капеллан (`bpriest = True`), все шаги 1–4
пропускаются. Вместо этого `target.hp := target.hp + indamage`,
ограниченное `maxhp` сверху [^8]. То есть Капеллан **прибавляет**
здоровье цели вместо нанесения урона. См.
[Выбор цели и атака с движением §7](target_selection.md) о том, как Капеллан
выбирает кого лечить.

### Шаг 6. Минимальный урон

Если после шагов 1–4 значение `damage < 1`, оно поднимается до 1;
затем `target.hp := target.hp − damage` [^9]. Минимум **один пункт
здоровья** снимается всегда, даже если все модификаторы вытеснили
урон в `0` или ниже. Это работает как «даже отскочившая пуля
кого-то сбила с ног». Для отдельного рукопашника-ветерана против
тяжёлой пехоты в строю с удержанием позиции это гарантирует
ненулевой урон.

После уменьшения `hp` проверяется смерть: при `hp <= 0` выставляется
`bdead := True` и вызывается `_misc_OnDeath`. Это отдельная
процедура, в которой:
- засчитывается `+kill` атакующему,
- начисляются очки счёта (`kill = +2 × cost`),
- запускается анимация смерти,
- освобождается слот в формации,
- проверяется `bfamine` (вдруг ушёл потребитель еды, см.
  [Голод и бунт наёмников](../economy/hunger_and_rebellion.md)).

<a id="3-хедшот-отдельная-ветка-flooruniqrnd--500"></a>
## 3. Попадание в голову

Бонус за попадание в голову рассчитывается отдельной веткой
`+floor(uniqrnd × 500)`. Она срабатывает **до** шага 4, но не заменяет
его. Условия [^5]:

1. Тип оружия: Сила выстрела (`bullet`) или Стрелы (`arrow`).
2. Цель — не здание (`not bbuilding`).
3. Цель — **не быстрая конница в движении** (для них уже отнимается
   −5, см. §2 шаг 1).
4. Проверка генератора случайных чисел: `random < 0.05` (шанс 5%).

Если все четыре истины — `damage := damage + floor(target.uniqrnd × 500)` [^10].

`uniqrnd` ∈ `[0, 1)` фиксируется при появлении юнита и больше не
меняется (см. [генератор случайных чисел Cossacks 3](../../../../internals/engine/rng_implementation.md)).
То есть один и тот же юнит **всегда** даёт один и тот же бонус
за попадание в голову — это часть детерминированной модели синхронизации.

Дальше формула продолжается обычным шагом 4 (вычитание `protection`).
Бонус может превратить слабый удар (1–2 урона после щита) в
смертельный (200–500 урона), мгновенно убивая обычного пехотинца
или крестьянина.

<a id="31-замечание-про-random"></a>
### 3.1. Почему случайный результат остаётся одинаковым у всех игроков

Перед проверкой 5%-шанса в `unit.script` стоит
`SetRandomKey(floor(uniqrnd × gc_MaxInt))` — пересев глобального
генератора случайных чисел из `uniqrnd` атакующего. Это
**отдельное детерминированное начальное значение для каждого
решения** (см.
[генератор случайных чисел Cossacks 3, §5](../../../../internals/engine/rng_implementation.md)),
гарантирующий что одно и то же попадание у всех клиентов даёт
одинаковый результат.

## 4. Дружественный огонь

Намеренно выбрать союзника целью нельзя: автоматический поиск и ручная атака
отсеивают своих. Однако уже выпущенный снаряд способен задеть союзника на
линии огня, а взрыв — любого в радиусе. Поэтому запрет на выбор своей цели
не равен полной защите от дружественного огня.

Снаряды с уроном по области — отдельная история. Граната, ядро,
мортирная бомба и
картечь приземляются по координате (или по уже выбранной вражеской
цели), а затем поражают **все** объекты в радиусе. Подробности — в §5
и §6.6 ниже.

Лечение Капеллана, наоборот, выбирает только союзные цели (см.
[Выбор цели и атака с движением](target_selection.md)).

Захват вражеского объекта — отдельная механика, не основанная на уроне. См.
[Как захватываются здания и юниты](../economy/capture_mechanics.md).

---

## 5. Урон по области — взрывная волна

Гранаты, ядра и картечь поражают не одну цель, а зону. После приземления:

1. Игра находит **все** объекты в радиусе поражения.
2. Урон каждого объекта уменьшается по расстоянию:
   ```
   damage_at_d = indamage × (1 − d / radius)
   ```
   где `d` — евклидово расстояние до эпицентра. Суммарный урон по
   всем зацепленным целям ограничен (см. §6.5 ниже).
3. Дружественный огонь **возможен**: если своя пехота стоит
   рядом с врагом, граната попадёт по обоим.

Предел урона по области ограничивает суммарный урон по группе целей: даже
если в радиус попало 30 юнитов, общий урон не может превысить
`damage × cap` (типично `cap = 3..5` юнитов-эквивалентов). Это
защищает кучкование от мгновенного уничтожения одной гранатой.

<a id="6-мирное-время-gboolpeacemode"></a>
## 6. Мирное время

Во время установленного в лобби периода мира формула пропускается особой
веткой [^6]. Поведение:

| Атакующий на чужой территории? | Цель на чужой территории? | Что |
|---|---|---|
| Нет | Нет | Атакующий мгновенно умирает. |
| Да | Да | Удар проходит как обычно. |
| Да | Нет | Атакующий мгновенно умирает; цель не получает урона. |
| Нет | Да | Атакующий мгновенно умирает; цель **тоже** мгновенно умирает (странность движка). |

«Чужая территория» определяется по карте владения, заполненной во время
генерации (см. [Как создаётся случайная карта](../map/map_generation_pipeline.md)).

Когда заданное в лобби время истекает, игра возвращается к обычной
шестишаговой схеме.

## 6.5. Ограничение урона по области

Взрывы ядра, бомбы, гранаты или картечи охватывают всех юнитов в радиусе
`r`, **но урон получают только первые N** [^11]:

```
count = floor(1 + (r / 0.35)²)
```

| Оружие | Радиус | Максимум юнитов под взрыв |
|---|---:|---:|
| Пушка, ядро | ~1 клетка | **9** |
| Мортира, бомба | ~2 клетки | **33** |
| Гаубица | ~1 клетка | **9** |
| Граната | ~0,5 клетки | **3** |

**Стратегический вывод:** плотная толпа защищена — 50 юнитов в
одной точке теряют максимум 9 от ядра, остальные нетронуты.
Растянутая линия страдает гораздо больше.

Огненные стрелы работают по другой ветке [^12]. Если в собранном по площади списке
**больше 300** юнитов — попадание идёт по всему списку без
проверки дистанции. Если **300 или меньше** — нужен `dist < r`.
Ограничение по числу целей в этой ветке не применяется.

## 6.6. Дружественный огонь

На этапе применения урона **нет общей проверки на сторону или владельца**
[^13]. Урон может получить любой объект на траектории.

**Что может попасть по своим:**
- обычные и огненные стрелы;
- мушкетные пули;
- гранаты;
- артиллерийские снаряды;
- Взрывы с уроном по области (картечь, ядра, бомбы) — поражают всё в радиусе,
  включая своих.

**Исключения:**
- **Корабли** имеют отдельную защиту [^14] — торговые и боевые
  корабли одного игрока не топят
  друг друга.
- **Башни и пушки** по умолчанию
  не стреляют, если на линии огня находится дружественное здание [^15].
  Это блокирует выстрел,
  а не урон при пролёте.

Точный список снарядов, у которых проверка линии огня отключена, приведён в
[технических подробностях](#технические-подробности).

## 6.7. Подтверждённые упрощения формулы

Несколько механик, привычных по другим стратегиям в реальном
времени, в Cossacks 3 **не
реализованы**. Каждый пункт — результат прямого поиска по
скриптам:

- **Бонуса за кавалерийский натиск нет.** Урон кавалерии равен базовому
  урону её оружия.
- **Отдельного типа урона против лошадей нет.** У Пикинера нет
  множителя «×N против кавалерии». Эффективность Пикинера против
  Рейтара объясняется уроном пики и низкой защитой кавалерии от этого
  типа оружия.
- **Ауры барабанщика нет.** Барабанщик — слот формации,
  «наполнение» отряда. Бонусов к урону / скорости / морали не
  даёт.
- **Особой траектории у гренадёра нет.** Гренадёр использует
  общий расчёт урона по области (тип Урон от ядер, `cannonball`,
  с радиусом взрыва).
- **Скрытности и невидимости нет.** Все юниты видны в зоне обзора.

Что из этого следует: формация — единственный способ умножить
урон. Никаких скрытых бонусов от позиции, кроме возвышенности (см.
[Как ведут себя стрелковые юниты §7](ranged_units_behavior.md)) и
удержания позиции. Улучшения, строй и соответствие
«тип оружия ↔ тип
брони» — это вся боевая математика.

## 7. Сценарная неуязвимость

Юниты с бесконечным запасом здоровья, декоративные персонажи и служебные
объекты сценария пропускают весь расчёт [^2]. Это
используется в кампании и исторических битвах для:

- Боссов, которых нельзя убить через урон (только через триггер).
- Декоративных гражданских (бегающие по карте крестьяне в
  заданиях, которые игрок не должен случайно перебить).
- Сценарных «маяков» — невидимых служебных объектов.

Такая защита активна только в сценарии: в случайной и сетевой игре этот
механизм не срабатывает.

---

## 8. Реакция отряда под управлением ИИ на удар

После снижения здоровья цели игра проверяет её принадлежность к отряду. Если отряд
находится без приказа или удерживает позицию, переводит весь отряд в режим
«атакую того, кто бьёт». Эффект: **один удар
будит весь отряд** — это часть «реалистичной» механики Cossacks,
когда залп по одному юниту немедленно вызывает ответ всех
соседей. См. подробности в
[Выбор цели и атака с движением §6](target_selection.md).

## Технические подробности

Основной обработчик — `_misc_DoDamage(goHnd, trgHnd, indamage, weapind,
weapkind)` [^1].

| Аргумент или поле | Значение |
|---|---|
| `goHnd` | дескриптор атакующего; может быть `0` для урона без источника |
| `trgHnd` | дескриптор цели; при `0` обработчик выходит |
| `indamage` | базовый урон оружия |
| `weapind` | индекс оружия у объекта |
| `weapkind` | тип оружия `gc_obj_weapon_kind_*` |
| `pobj2`, `bdead` | существование цели и состояние смерти |
| `gbool_peacemode` | включённое мирное время |
| `gc_gameplay_infinitehp`, `gScenario.bactive` | сценарная неуязвимость |
| `_unit_IsOnEnemyTerritory`, `OwnerMap`, `FillOwnerMap` | проверка чужой территории |
| `_misc_DoRoundDamage` | урон по области |
| `bcheckfriendonline`, `_misc_IsBuildingInRay` | проверка дружественного здания на линии огня |
| `bcharging`, `firsthit`, `chargebonus`, `bstealth` | отсутствующие в скриптах признаки натиска и скрытности |

Проверка дружественного здания на линии огня явно отключена у
`STRELA`, `OSTRELA`, `SHOTMUSKET`, `SHOTBLOCKHOUSE`, `NUCLGRE`,
`PSMPOINTTPUS`, `DIMMORT1`, `DIMMORT2NEW`, `PSMPOINTT` и `DIMMORT2KOR`.

## Открытые эмпирические вопросы

1. **Точная формула предела урона по области**: похоже, что `cap = 3..5`
   юнитов-эквивалентов суммарного урона, но коэффициент в коде
   не вычитан. Замерить через серию выстрелов гранатой по группе
   из 1, 5, 10, 20, 50 юнитов и сверить.
2. **Чёткие условия `peacemode` 4-го типа** (атакующий на своей,
   цель на чужой → оба умирают): это похоже на баг в скрипте,
   нужно подтвердить. Если так — стоит добавить в
   [список известных ограничений](../../../../internals/project/known_issues.md).
3. **Учёт попадания в голову при отрицательном базовом уроне.** Если шаг 1–4
   уже свели `damage` к `< 0`, и затем бонус добавил `+200`,
   получится ли `damage = 200` или `damage = max(1, ...) + 200`?
   Кодом порядок шагов нечитается без полного дизассемблирования
   ветки `_misc_DoDamage`.

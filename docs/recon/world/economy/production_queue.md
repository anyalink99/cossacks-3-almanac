# Очередь производства

[← Как устроена игра](../../README.md)

Глубокий разбор: как устроена очередь заказов в зданиях
(казарма / академия / конюшня / ратуша), как работают повторы и
бесконечный режим, что происходит при отмене, при захвате, при
сносе. Все ссылки на код — в [Источниках](#источники).

> **Связанные документы:**
> [`building_mechanics.md` §6.3](building_mechanics.md) — refund при
> отмене / разрушении; [`upgrades_application.md` §3](upgrades_application.md)
> — отдельная очередь для апгрейдов;
> [`unit_commands.md`](../combat/unit_commands.md) — общая модель
> приказов на юнитах (тоже использует `gOrders`).

## TL;DR

- Здание держит до **`gc_obj_MaxOrderCount = 12`** одновременных
  ордеров [^1]. Это общий лимит на все типы (производство,
  апгрейд, ремонт и т. п.), не на каждый отдельно.
- Каждый ордер на производство — это запись `TOrder` с полями
  `produceid` (sid юнита), `amount` (сколько ещё произвести),
  `progress` (прогресс текущего экземпляра), `restype` (счётчик
  built-копий **на момент заказа** — нужен для refund).
- `amount = -1` (`gc_obj_order_produce_infinite`) означает
  **бесконечный режим** — здание производит юнита, пока заказ не
  отменят явно.
- **Заказ того же юнита в существующий ордер сливается**: если в
  очереди уже есть `peaaus`-ордер и `costpercent = 100` (или
  ноль) — новые `peaaus` добавятся к `amount` существующего, не
  создадут отдельный ордер.
- При различном `costpercent` (`peaaus` дорожает с каждым новым)
  слитие случается только если `unitcount = restype` — то есть
  игрок не успел построить других юнитов того же типа между
  заказами.
- **Захватчик рядом останавливает производство.** Если в зоне
  scan-grid у здания появляется `bcancapture`-юнит противника без
  `bprotector`-защитника — здание **прекращает** прогресс заказа.
- При сносе здания все ордера прокручиваются обратно — оплаченные
  юниты и апгрейды возвращаются игроку (см.
  [`building_mechanics.md` §6.2](building_mechanics.md)).

## 1. Структура ордера на производство

`TOrder` — запись в массиве `TObj.orders[0..gc_obj_MaxOrderCount-1]` [^1].
Поля для типа `gc_obj_order_type_produce = 4`:

| Поле | Что |
|---|---|
| `itype` | Тип ордера. `4` = производство юнита. Полный список — см. §1.1. |
| `info.produceid` | sid юнита, который производим. |
| `info.amount` | Сколько ещё произвести. `-1` (`gc_obj_order_produce_infinite`) = бесконечно. |
| `info.progress` | Прогресс текущего экземпляра (`0..buildtime`). |
| `info.restype` | Счётчик built-копий **в момент заказа**. Используется в `_unit_CancelUnitProduction` для возврата правильной суммы при `costpercent ≠ 100`. |

### 1.1. Все типы ордеров (`gc_obj_order_type_*`)

| ID | Тип | Применение |
|---:|---|---|
| 0 | `none` | Пустая ячейка очереди. |
| 1 | `move` | Идти в точку. |
| 2 | `attackobj` | Атаковать конкретного юнита. |
| 3 | `gainres` | Добывать ресурс. |
| 4 | `produce` | **Производство юнита** (эта статья). |
| 5 | `patrol` | Патрулирование. |
| 6 | `attackpoint` | Стрельба по точке (артиллерия). |
| 7 | `continueattackpoint` | Продолжение атаки точки. |
| 8 | `performupgrade` | **Исследование апгрейда.** |
| 9 | `fishing` | Рыболовство (для `fishboat`). |
| 10 | `creategates` | Постройка ворот. |
| 11 | `buildwallcontinue` | Продолжение постройки стены. |
| 12 | `buildwall` | Постройка стены. |
| 13 | `gotomine` | Идти в шахту. |
| 14 | `gototransport` | Идти в транспортный корабль. |
| 15 | `leavetransport` | Выйти из транспорта. |
| 16 | `leavebuilding` | Выйти из здания (гарнизон). |
| 17 | `build` | Строить здание. |
| 18 | `guard` | Охранять. |
| 19 | `repair` | Ремонтировать. |
| 20 | `exitunits` | Выпустить всех юнитов из гарнизона. |

`MaxOrderCount = 12` ордеров **общий** лимит — то есть здание
может одновременно держать смесь из, например, 5 ордеров на
производство, 2 на апгрейд и 1 на ремонт. Юнит-боец же обычно
использует только `move`, `attack`, `guard` и т. п., но лимит
тот же.

## 2. Добавление ордера в очередь

`_unit_OrderProduce(goHnd, ordercid, orderid, amount)` [^2]:

1. Проходит по существующим ордерам с конца (`MaxOrderCount-1
   downto 0`).
2. Ищет существующий ордер того же `produceid`.
3. **Если нашёл и условия слития подошли** (см. §2.1) — увеличивает
   `amount` существующего ордера.
4. **Если не нашёл** — добавляет новый ордер в первую свободную
   ячейку через `_unit_AddOrder` [^3].
5. Если ячейки кончились (12 заняты) — заказ **отбрасывается**
   молча.

### 2.1. Условия слития ордера

Ордера сливаются (новые юниты добавляются к существующему `amount`)
если:

- **`costpercent = 100`** (цена не растёт) — всегда сливается.
- **`costpercent = 0`** (специальный «без масштабирования») —
  тоже сливается.
- **`unitcount = order.restype`** — игрок ещё не построил ни
  одного юнита этого типа после первого заказа. Тогда `costmodifier`
  для refund остаётся актуальным, и слитие безопасно.

В остальных случаях создаётся **новый** ордер с правильным
`restype = unitcount` (текущий счётчик). Это критично для refund:
если бы можно было всё слить в один ордер, а игрок построил 5
дорогих юнитов между заказами, refund был бы рассчитан с
неактуальным `costmodifier`.

### 2.2. Бесконечный режим

`amount = gc_obj_order_produce_infinite = -1` означает «продолжать
до явной отмены». Когда `_unit_OrderProduce` встречает
существующий бесконечный ордер и приходит запрос с конкретным
числом (`amount > 0`) — конкретный заказ **игнорируется** (внутри
бесконечного и так всё произведётся).

Зеркальная семантика в `_unit_CancelUnitProduction` с
`bConvertToInfinite = True` [^4]: один отменяемый юнит из конечного
ордера может **превратить** ордер в бесконечный (если `amount`
дошёл до 0 или 1).

## 3. Прогресс и завершение

Каждый игровой тик функция `_unit_DoOrderProgress` (находится в
`units/global.inc` или подобном) увеличивает `info.progress` на
`deltatime × buildtime_modifier`. Когда `progress >= buildtime`:

1. Создаётся юнит через `_unit_ProduceUnit` [^5].
2. Юнит спавнится у `rallypoint` здания (или у входа, если rally
   не задан).
3. `info.amount -= 1`. Если стал 0 — ордер завершён, удаляется.
4. Если `amount = -1` (бесконечный) — заказ продолжается.

`_unit_ProduceUnit` распределяет производство **по нескольким
зданиям одного типа**: если в `list` несколько казарм, выбирается
та, у которой минимальный `produceind` (т. е. меньше всего
заказов в очереди). Это автоматическая балансировка: игрок может
запросить «20 пикинёров со всех казарм», и они равномерно
распределятся.

## 4. Отмена заказа

`_unit_CancelUnitProduction(goHnd, cid, unitID, amount, bConvertToInfinite)` [^4]:

1. Находит ордер с нужным `produceid`.
2. Уменьшает `info.amount` на 1.
3. Если `amount` дошёл до 0:
   - **Без bConvertToInfinite** — обнуляет `progress` и удаляет
     ордер.
   - **С bConvertToInfinite** — превращает в `gc_obj_order_produce_infinite`
     (заказ продолжится бесконечно).
4. **Refund**: если ордер был «оплачен» (`amount > 0` или
   `progress > 0`) — возвращает игроку:
   ```
   refund[k] = price[k] × (costpercent / 100)^(restype + i)
   ```
   То есть точно столько, сколько было списано в момент заказа.

Refund действует **по 1 юниту за вызов** — в цикле `i:=0 to
Abs(amount)-1`. То есть отмена 5 пикинёров вернёт ровно 5 цен,
каждая с актуальным `costmodifier` для своей позиции в счётчике.

## 5. Прерывание производства захватчиками

`_unit_CheckCapturersStopProduce(goHnd)` [^6] вызывается каждый
тик прогресса. Алгоритм:

1. Берёт `scangridx`, `scangridy` здания и расширяет на `rx1 = 1`
   ячейку scan-grid'а в каждую сторону.
2. В ячейках со включённым `enemyplmask` ищет вражеский
   `bcancapture`-юнит через `_unit_SearchCapturers`.
3. Если найден — проверяет, есть ли у него `bprotector`-защитник
   рядом. Если **нет** защитника — возвращает `True`, и
   производство в этом тике **не прогрессирует**.

**Особый случай:** стены (`bwall`-здания). Если HP стены ниже
трети `maxhp`, проверка пропускается — стену уже почти разрушили,
имеет смысл достроить её до конца.

Эффект: рейд кавалерией к казарме не только захватывает её, но и
**замораживает производство** ещё до захвата. Защитник
(`bprotector`) рядом снимает заморозку.

## 6. Захват здания с очередью

При `_misc_ChangePlayer` (захват) у здания все ордера на
производство и апгрейды:

1. Прогоняются через `_unit_CancelUnitProduction(... bState=False)`
   и `_unit_CancelUpgradePerform` соответственно.
2. Ресурсы возвращаются **прежнему** владельцу (через `bProcess`
   проверку), не новому.
3. Очередь нового владельца стартует пустой — он может сразу
   ставить свои заказы.

Это значит: **захватив казарму противника, ты не получишь его
заказы автоматически**. Если хочешь продолжать клепать те же
юниты, нужно ставить свои ордера. Но: **обратно прежний владелец
получит refund** — это уже вложение в «спорное» здание, которое
тебе не достанется.

---

## 7. Снос здания с очередью

При `bDie := True` или `hp <= 0` `OnDeath`-хук тоже прогоняет всю
очередь через cancel-функции [^7]. То есть **разрушение собственной
казармы во время производства возвращает ресурсы**.

На практике редкий случай: если ИИ или капкан разрушают твою
работающую казарму, ты получаешь обратно стоимость недопроизведённых
юнитов. Это смягчает ущерб от рейда.

---

## 8. Очередь апгрейдов

Параллельно с производством здание может держать ордера типа
`gc_obj_order_type_performupgrade = 8` через `_unit_OrderUpgrade`.
Семантика похожа:

- Один и тот же апгрейд **нельзя** заказать дважды (проверка через
  `gPlayer[pl].upgstate[cid][upgind]`).
- Cancel возвращает базовую стоимость апгрейда (без
  `costpercent`-масштабирования — у апгрейдов его нет).
- Завершение исследования применяет эффект и удаляет ордер.

Подробнее — в [`upgrades_application.md`](upgrades_application.md).

---

## 9. UI-ограничения

Помимо технического `MaxOrderCount = 12`, игрок видит в UI здания
**пять или шесть слотов** очереди. Превышение запрещается на
GUI-уровне: кнопка «заказать ещё» становится неактивной. Это
обеспечивает запас на ордера ремонта / упрощает визуализацию
прогресс-бара.

Точная UI-логика — в `lib/gui.script`, не в логике производства.

## 10. Открытые эмпирические вопросы

1. **Точная скорость прогресса.** `info.progress += delta` —
   `delta` пропорциональна `buildtime_modifier × deltatime` плюс
   множитель сложности (для ИИ — `0.30 / 0.50 / 0.75 / 1.00 / 1.25`,
   см. [`../../systems/ai_behavior.md`](../../systems/ai_behavior.md)).
   Точные коэффициенты — не вычитаны из кода.
2. **Сколько слотов реально в UI на разных размерах окна.** В
   широком экране может быть 7–8, в стандартном — 5. Замерить.
3. **Блокировка производства при захвате — в течение скольких
   тиков прогресс не идёт?** Один тик «нашли захватчика» или весь
   период пока он в радиусе?

# Recon: сценарии и триггеры

Глубокий разбор: как устроены сценарии (Historical Battles и
кампания) — что такое триггер, условие, действие, состояние FSM.
Все ссылки на код — в [Источниках](#источники).

## TL;DR

- Сценарий — это файл `.parser` с описанием состояния FSM,
  загруженный через `gScenario` [^1].
- Триггер (`TScenarioTrigger`) — пара «условие + действие».
  Когда условие истинно, действие исполняется один раз.
- Условие (`TScenarioCondition`) — проверка состояния игры:
  «у игрока N юнитов», «здание X разрушено», «игрок дошёл до точки».
- Действие (`TScenarioAction`) — изменение состояния: «спавн юнита»,
  «текст на экране», «переход в следующее состояние FSM».
- FSM (`TScenarioStateMachine`) переключает наборы триггеров: в
  состоянии «бой» работают одни триггеры, в состоянии «победа» — другие.
- Сценарии используют **inline DWS-скрипты** через поле
  `OnLoadScriptFileName` (см.
  [`scripts/structure.md` §3](../../../internals/scripts/structure.md)).
- Активный сценарий помечен `gScenario.bactive = True` — это
  включает специальные эффекты (неуязвимость для `hp >= gc_gameplay_infinitehp`,
  отдельную обработку peace-mode и т.д.).

## 1. Структура сценария

Сценарий описывается в `.parser` файле, обычно лежит в
`data/maps/` или встроен в кампанию. Корневые объекты:

| Объект | Что |
|---|---|
| `TScenarioStateMachine` | Конечный автомат состояний сценария. |
| `TScenarioState` | Одно состояние (например, «бой», «победа», «диалог»). |
| `TScenarioTrigger` | Триггер — связка `condition → action`. |
| `TScenarioCondition` | Условие триггера. |
| `TScenarioAction` | Действие триггера. |
| `TScenarioResult` | Результат сценария (победа/поражение/специальный). |
| `TScenarioQuery` | Запрос к состоянию игры (для сложных условий). |

Главный объект — `gScenario`, единственный экземпляр на партию.

---

## 2. Триггер

Триггер — это запись с двумя ключевыми полями: условие
(`TScenarioCondition`) и действие (`TScenarioAction`).

### 2.1. Жизненный цикл

1. При активации состояния FSM все его триггеры **подключаются**
   к проверке.
2. Каждый игровой тик (или с заданной периодичностью) скрипт
   проверяет условие каждого активного триггера.
3. Когда условие истинно — действие исполняется.
4. После исполнения триггер **деактивируется** (если он
   `single-shot`) или остаётся для повторного срабатывания
   (`repeating`).

### 2.2. Типичные условия

`TScenarioCondition` поддерживает множество шаблонов:

| Тип | Что проверяет |
|---|---|
| `unit_count_le(player, sid, N)` | У игрока N юнитов конкретного типа стало ≤ N. |
| `unit_count_ge(player, sid, N)` | …стало ≥ N. |
| `building_destroyed(handle)` | Здание разрушено. |
| `unit_at_point(handle, x, z, radius)` | Юнит в радиусе от точки. |
| `time_elapsed(seconds)` | Прошло N игровых секунд от начала состояния. |
| `resource(player, type, op, amount)` | Ресурс игрока ≥/≤ N. |
| `flag_set(name)` | Сценарный флаг установлен. |
| `composite (AND, OR, NOT)` | Комбинация условий. |

### 2.3. Типичные действия

`TScenarioAction` поддерживает:

| Тип | Что делает |
|---|---|
| `spawn_unit(player, sid, x, z)` | Создать юнит. |
| `give_resource(player, type, amount)` | Прибавить ресурс. |
| `show_text(text_id, duration)` | Показать сообщение на экране. |
| `play_sound(sound_id)` | Воспроизвести звук. |
| `transition_to_state(state_name)` | Переключить FSM в другое состояние. |
| `set_flag(name)` | Установить сценарный флаг. |
| `set_unit_invincible(handle, true)` | Сделать юнит неуязвимым. |
| `script(code)` | Выполнить inline DWS-код (для нестандартных эффектов). |

## 3. FSM состояний

Сценарий — это **конечный автомат**, в котором каждое состояние
имеет свой набор активных триггеров. Это позволяет разделять
этапы:

| Этап | Активные триггеры |
|---|---|
| `intro` | Показать заставку, дождаться клика — переход. |
| `setup` | Дать ресурсы игроку, разместить отряды. |
| `combat_phase_1` | Триггеры для первой волны атаки противника. |
| `combat_phase_2` | После победы в фазе 1 — спавн новой волны. |
| `victory` | Показать концовку, начислить очки. |
| `defeat` | Сообщение о поражении. |

Переход между состояниями делается через
`transition_to_state(name)`. Скрипт выгружает старые триггеры,
загружает новые. См. также `TFormStateMachines` в нативном API
[^2].

## 4. Inline-скрипты

Сложные действия (которые не покрываются стандартными
`TScenarioAction`-типами) реализуются через inline-DWS-скрипты.
Поле сценария `OnLoadScriptFileName` указывает на отдельный
`.script`-файл, который загружается при активации состояния FSM.

Этот файл содержит обычные DWS-функции, которые могут вызывать
любой нативный API (см.
[`internals/engine/native_api.md`](../../../internals/engine/native_api.md))
и читать `gScenario.*`-поля.

Это даёт сценаристам полную мощь скриптов: можно делать
произвольную логику диалогов, союзников, кастомные триггеры.

---

## 5. Особые эффекты `gScenario.bactive`

Когда `gScenario.bactive = True`, движок включает несколько
особых поведений:

1. **Сценарная неуязвимость**: юниты с `hp >= gc_gameplay_infinitehp`
   или `not GetGameObjectPlayableObjectByHandle(handle)` не получают
   урон (см. [`combat_damage_pipeline.md` §7](../world/combat/combat_damage_pipeline.md)).
2. **Peace-mode** (`gbool_peacemode`) обрабатывается особым
   образом — игрок-герой может атаковать только определённых
   противников.
3. **Союзный обзор** (`AddFOWPlayers`): главный игрок (plInd = 0)
   не делится обзором с **нейтральными** персонажами кампании
   (см. [`vision_and_fow.md` §4.2](../world/combat/vision_and_fow.md)).
4. **AI**: ИИ-противники в сценарии используют отдельные правила
   (часто ручная скриптовая агрессия, не стандартный
   `_ai_DoTickAggressive`).

## 6. `TScenarioQuery` — запросы к состоянию

Когда условие триггера не покрывается простыми `unit_count` /
`resource`, используется `TScenarioQuery` — параметризованный
запрос. Например, «есть ли в радиусе R от точки (x, z) юниты
конкретного типа player'а P».

Запрос выполняется при каждой проверке триггера и возвращает
булев результат. Это позволяет делать гибкие условия без
переписывания на DWS.

---

## 7. `TScenarioResult` — итоги

Финальное состояние сценария — `TScenarioResult`. Возможные
значения:

| Result | Что |
|---|---|
| `victory` | Игрок победил, концовка положительная. |
| `defeat` | Поражение. |
| `draw` | Ничья (редко). |
| `next_mission(id)` | В кампании — переход к следующей миссии. |
| `replay_mission` | Повтор той же миссии (по выбору игрока). |

При завершении сценария скрипт пишет результат в
`gCampaignProgress` — структуру с прогрессом по всей кампании.
Эта структура сохраняется на диск (см. также
[`internals/engine/server_sync_packet_format.md`](../../../internals/engine/server_sync_packet_format.md)).

## 8. Где живут сценарии

| Файл | Что |
|---|---|
| `data/maps/<scenario>.aix` | Бинарный формат сценария (компилированный?). |
| `data/maps/<scenario>.map` | Сама карта (terrain, начальные юниты). |
| `data/scripts/lib/scenario.script` | Базовая скриптовая логика обработки сценариев (~200 КБ кода). |
| `data/scripts/lib/scenarioeditor.script` | Редактор сценариев (для разработчиков и моддеров). |

Парсер сценариев — нативный (через `Parser*ValueByKeyByHandle`),
скрипт `lib/scenario.script` загружает структуры триггеров и
условий через эти вызовы.

---

## 9. Открытые эмпирические вопросы

1. **Точный синтаксис `.aix`-файла**. Бинарный формат сценария,
   который не разобран. В текущем проекте `.aix` файлы не
   парсятся.
2. **Лимит на количество триггеров в одном состоянии**. Похоже,
   нет жёсткого лимита, но при большом числе (>100) частота
   проверки может проседать.
3. **Когда применяется `transition_to_state` относительно
   действия**. Триггер сначала исполняет все свои действия,
   потом переключает состояние? Или новое состояние начинает
   обрабатываться сразу после `transition`?
